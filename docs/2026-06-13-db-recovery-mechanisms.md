# 数据库恢复机制

数据库系统运行过程中发生故障时，恢复机制可以将数据库恢复到故障前的某个一致性状态。

常用的恢复机制包括：

- 日志技术
- 数据库转储

## 1. 故障类型与恢复

事务故障的恢复

- 当发生事务故障时，恢复子系统应利用日志文件撤销此事务已对数据库进行的修改。
- 事务故障的恢复通常由系统自动完成，用户并不知道系统是如何进行事务恢复的。

系统故障的恢复

- 系统故障恢复操作要撤销故障发生时未完成的事务，重做已完成的事务。
- 系统故障的恢复由系统在重新启动时自动完成，不需要用户干预。

介质故障的恢复

- 介质故障会破坏磁盘上的物理数据库和日志文件，这是最严重的一种故障。
- 应对方式：
  - 使用 RAID 等技术提高介质可靠性。
  - 定期转储备份。
  - 出故障后重装转储文件。

稳定存储器

- 准确来说应是接近稳定存储器，用于存放日志文件。

## 2. 日志

更新日志记录：

```text
<Ti, Xj, Vo, Vn>
```

含义：事务 `Ti` 对数据项 `Xj` 执行了一项写操作，`Xj` 的值由 `Vo` 变成 `Vn`。

**先写日志**：日志在数据库修改前输出到日志文件，这样系统才有能力撤销对数据库的修改。

## 3. 检查点

检查点用于减少故障恢复时需要扫描的日志范围。

如果没有检查点，系统崩溃后可能要从日志开头一直扫到最后，才能判断哪些事务要重做、哪些事务要撤销。

例如日志很长：

```text
很久以前的日志 ... 检查点 C ... T1 start ... T2 start ... T1 commit ... 崩溃
```

恢复时不需要从“很久以前的日志”开始扫，只需要从检查点 `C` 附近开始。这样可以跳过大量已经稳定落盘的历史操作。

### 普通检查点

普通检查点会暂停新的更新操作，然后完成三件事：

- 将当前位于主存的所有日志记录输出到日志文件。
- 将主存中所有脏页输出到磁盘。
- 写入一条检查点日志：

```text
<checkpoint L>
```

其中 `L` 是检查点发生时仍然活跃的事务列表。

恢复时，从最近的检查点开始看：

- 检查点时已经提交、且脏页已落盘的事务，一般不用再关心。
- `L` 中的事务，检查点时还没结束，需要继续判断。
- 检查点之后启动的事务，也需要继续判断。

所以恢复重点是：

```text
检查点中的活跃事务 L + 检查点之后启动的事务
```

例子：

```text
<T1 start>
<T1 commit>
<T2 start>
<checkpoint {T2}>
<T3 start>
<T3 commit>
崩溃
```

恢复时重点看 `T2` 和 `T3`：

- `T2` 在检查点时还活跃，崩溃前没有 commit，需要撤销。
- `T3` 在检查点后启动，并且已经 commit，需要重做。
- `T1` 在检查点前已经提交，通常不用再扫描处理。

普通检查点的问题是：如果脏页很多，暂停更新的时间会很长。

### 模糊检查点

模糊检查点的目标是减少暂停时间。

它不会等所有脏页都写完才让系统继续运行，而是先快速写入：

```text
<checkpoint L>
```

然后系统马上恢复更新，脏页在后台慢慢写回磁盘。

等这批脏页全部写完后，系统再记录这个检查点已经成为：

```text
full_checkpoint
```

`full_checkpoint` 表示“这个检查点对应的脏页已经全部落盘”。系统恢复时，从最近的 `full_checkpoint` 开始扫描日志。

脏页后台写回时仍然必须遵守**先写日志**规则，并在写页时使用闩锁，避免页正在写出时又被修改。

## 4. 事务 Ti 回滚

从后向前扫描日志。对于发现的每条日志记录：

```text
<Ti, Xj, Vo, Vn>
```

执行：

- 将值 `Vo` 写入 `Xj`。
- 往日志中输出一条 redo-only 日志记录：

```text
<Ti, Xj, Vo>
```

- 一旦发现：

```text
<Ti, start>
```

就停止扫描，并往日志中输出：

```text
<Ti, abort>
```

## 5. 系统崩溃后的恢复

### 重做阶段

目标：重回崩溃点的系统状态，并顺便构建 `undo-list`。

从最后一个检查点开始正向扫描日志文件，重放所有更新，包括崩溃前已回滚的记录。

规则：

- 将 `undo-list` 置为 `<checkpoint L>` 中的 `L`。
- 对于以下记录，将 `V2` 值写给 `Xj`：

```text
<Ti, Xj, V1, V2>
<Ti, Xj, V2>
```

- 对于以下记录，将 `Ti` 加入 `undo-list`：

```text
<Ti, start>
```

- 对于以下记录，将 `Ti` 从 `undo-list` 中移除：

```text
<Ti, abort>
<Ti, commit>
```

### 撤销阶段

目标：回滚那些没有完成的事务，也就是没有 `commit` 或 `abort` 的事务。

- 对 `undo-list` 中的每个事务执行回滚操作。
- 实现上可以扫描一次，回滚列表中的所有事务。

## 6. 日志缓冲与数据库缓冲

为了减少磁盘 IO，数据库不会每产生一条日志、每修改一个数据页就立刻写磁盘。

通常会同时使用两类缓冲：

- 日志缓冲：日志先放在内存里，之后批量写入日志文件。
- 数据库缓冲：被修改的数据页先留在内存里，之后再写回磁盘。

这会带来一个问题：如果日志和数据页的写盘顺序错了，系统崩溃后就可能无法恢复。

核心规则仍然是**先写日志**：

```text
数据页写入磁盘前，相关日志必须已经写入日志文件。
```

例如事务 `T1` 把 `A` 从 100 改成 200：

```text
<T1, A, 100, 200>
```

如果数据页 `A = 200` 已经写入磁盘，但这条日志还没写入日志文件，系统马上崩溃，那么恢复时就不知道 `A` 原来是 100，也就无法撤销 `T1`。

所以写盘顺序必须是：

```text
先写日志 <T1, A, 100, 200>
再写数据页 A = 200
```

事务提交也有类似要求：

- `<T1, commit>` 写入日志文件后，`T1` 才算真正提交。
- 写入 `<T1, commit>` 前，`T1` 之前的所有日志都必须已经写入日志文件。
- 日志可以提前写入磁盘，提前写日志是安全的。

数据库缓冲还有两个常见策略：

- **强制 / 非强制**：事务提交时，是否立刻把它修改过的数据页写回磁盘。
- **窃取 / 非窃取**：事务提交前，是否允许把它修改过的数据页提前写回磁盘。

实际系统常用的是**非强制 + 窃取**：

- 非强制：提交时不必立刻写数据页，性能更好；如果崩溃，靠 redo 重做已提交事务。
- 窃取：未提交事务的数据页也可能提前写盘，缓冲区更灵活；如果崩溃，靠 undo 撤销未提交事务。

因此，只要遵守**先写日志**，即使数据页和日志都使用缓冲，系统仍然可以恢复到一致状态。

输出数据页时一般需要使用闩锁，避免页正在写出时又被修改：

1. 获取数据页的排他闩锁。
2. 先把与这个页相关的日志写入日志文件。
3. 再把数据页写入磁盘。
4. 释放闩锁。

## 7. 逻辑 undo 操作

逻辑 undo 指：回滚时不直接把数据项恢复成旧值，而是执行一个语义上相反的操作。

普通 undo 依赖这种日志：

```text
<Ti, Xj, V1, V2>
```

回滚时把 `Xj` 从 `V2` 写回 `V1`。

但很多操作不是单个数据项的修改，例如插入一行可能同时影响数据页、索引页和元数据。如果都记录 `V1`、`V2`，日志会很大。

并发场景下，直接写回旧值也可能覆盖其他事务的结果。例如余额先是 100：

```text
T1: +10
T2: +20
```

如果 T1 回滚，不能把余额直接写回 100，否则会抹掉 T2 的 `+20`。正确做法是执行反向操作：

```text
T1 undo: -10
```

所以逻辑 undo 记录的是“事务做了什么动作”，回滚时执行相反动作：

- 插入一行，对应删除这行。
- 删除一行，对应重新插入这行。
- 增加数值，对应减少数值。

## 8. ARIES

ARIES 是很多数据库采用的恢复思路，可以理解为对前面日志恢复机制的系统化版本。

它的核心目标是：

- 已提交事务的修改不能丢，要 **redo**。
- 未提交事务的修改不能留下，要 **undo**。
- 恢复过程中如果再次崩溃，下次还能继续恢复。

ARIES 有三个关键思想：

- **先写日志**：数据页写盘前，相关日志必须先写盘。
- **重复历史**：恢复时先把系统重做到崩溃时的状态，包括未提交事务的修改。
- **记录撤销过程**：undo 时也写日志，避免恢复过程中再次崩溃后从头撤销。

恢复过程分三步：

1. **分析阶段**

   从最近的检查点开始扫描日志，找出：

   - 崩溃时还没完成的事务。
   - 哪些数据页可能是脏页。

2. **重做阶段**

   从可能最早需要重做的位置开始，按日志顺序重放操作。

   这一步不只重做已提交事务，也会重做未提交事务。原因是 ARIES 要先“重复历史”，把数据库恢复到崩溃瞬间的样子。

3. **撤销阶段**

   对崩溃时未完成的事务，从后往前执行 undo。

   每撤销一步，都会写一条补偿日志记录（CLR，Compensation Log Record）。CLR 是“undo 的 redo 日志”。
     - 在 redo 阶段：要重做 CLR 对应的撤销动作。
     - 在 undo 阶段：不会再 undo 这个 CLR。

简单例子：

```text
T1 修改 A
T2 修改 B
T1 commit
系统崩溃
```

恢复时：

- 分析：发现 `T1` 已提交，`T2` 未完成。
- 重做：重做 `T1 修改 A` 和 `T2 修改 B`，先回到崩溃瞬间。
- 撤销：撤销 `T2 修改 B`，并写入 CLR。

所以 ARIES 可以总结为：

```text
先分析，再重做历史，最后撤销未完成事务。
```
