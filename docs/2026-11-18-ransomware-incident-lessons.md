# 数据库勒索事件处置指南

本文介绍数据库遭遇勒索加密后的处置方法、常见加密原理和恢复路线，以 SQL Server 为技术示例。具体操作应结合存储环境、备份形式和取证要求评估。

## 1. 分析前先区分事实与推测

文件后缀、可读字符串、高熵区段和尾部标记都只是线索，需要结合结构解析与交叉验证。建议为每条结论记录来源、验证方法和适用范围。

| 线索 | 可以判断的方向 | 不能直接得出的结论 |
| --- | --- | --- |
| 文件后缀 | 检索候选家族与工具 | 具体算法、攻击者身份或家族归属 |
| 周期性受损区段 | 验证间歇加密布局 | 业务数据损失比例 |
| 明文残留 | 评估局部数据提取 | 整条记录或整张表完整 |
| 备份描述符 | 识别容器与数据流 | 备份完整且可以还原 |
| 文件尾部变化 | 查找加密参数与恢复元数据 | 密钥独立随机或可直接提取使用 |
| 跨文件测试未命中 | 记录已测试假设和范围 | 所有密钥复用与实现缺陷均已排除 |

受害业务类型和所在地区也不足以证明攻击者来源或定向攻击，归因需要额外证据。

## 2. 勒索软件怎样让文件无法使用

### 2.1 常见过程

攻击者可能通过弱口令、漏洞、远控账户或其他入口进入服务器，取得权限后探查数据库和备份。随后可能停止业务服务、破坏恢复副本、投放加密程序，再写入勒索说明。不同事件不一定包含全部步骤，入口与数据外传情况需要分别调查。

备份若与生产数据共享主机、挂载权限或管理凭据，也会进入攻击者可写范围。因此“每天都有备份”与“攻击后仍有可恢复备份”是两件事。

### 2.2 混合加密与文件密钥

常见设计使用 AES、ChaCha20 等快速算法处理内容，再用公钥密码机制保护文件密钥。以下仅为一种常见设计的示意，实际实现因变种而异：

```text
文件 A ── 文件密钥 KA + nonce/IV ──→ 全部或部分内容被加密
                          │
                          └─→ 密钥受到保护后，与必要参数写入文件头/尾或其他位置

文件 B ── 文件密钥 KB + nonce/IV ──→ 另一个加密文件

攻击者保有的秘密 ──→ 恢复文件密钥 ──→ 还原内容
```

有的实现每个文件生成新密钥；有的共用密钥但使用不同 nonce；也有的通过临时密钥交换派生密钥。文件内可以保存受保护的密钥、临时公钥、nonce、原始长度和区段信息，而不保存可直接解密的私钥。

所以“密钥信息就在文件尾部”不意味着能直接取出来使用，也不一定是先写入明文密钥、再加密文件中的那一片区域。具体布局必须由样本或格式分析确认。

### 2.3 为什么只加密一部分

间歇加密通过跳过大量字节提高处理速度，同时破坏数据库页、索引或备份流，使正常软件无法使用文件。加密字节占整个文件的比例，不能直接换算为业务数据损失率。

数据库中的系统元数据、跨页记录、大字段和关联关系会放大局部损坏的影响。压缩备份还可能因压缩单元受损，使一段未直接加密的内容无法正常解压。看到大段明文是好线索，完整恢复仍需结构和业务验证。

### 2.4 对方提供解密器时，恢复是怎样完成的

如果对方确实持有正确秘密，解密器可读取文件内参数，恢复文件密钥，再逆向处理受损区段。这个过程依赖密钥，不是临时破解算法。

拿到工具也不等于恢复结束：错误版本、程序缺陷、原先已有的截断、加密时并发写入或重复加密，都可能导致输出仍损坏。一次小文件试解成功，也不能证明大型数据库备份完整可用。涉及联系或交涉时，应配合警方与事件处置负责人，保留全部原始记录。

## 3. 第一阶段：快速隔离，同时保存恢复机会

应优先停止继续破坏，再保留能影响后续恢复的证据。微软的勒索响应流程同样强调隔离与保留既有系统，见[事件响应指南](https://learn.microsoft.com/en-us/security/ransomware/incident-response-playbook-dart-ransomware-approach)。

1. **隔离受影响主机及备份访问路径。** 断开不必要网络，限制共享和远控通道，同时排查其他受影响设备。隔离网络不保证本机加密立即停止，仍需评估活动进程。
2. **评估易失证据与持续破坏。** 主机仍运行时，尽快由应急人员评估内存和进程取证；若无法阻止持续破坏，应优先止损。不要机械执行“一律不关机”或“一律立刻关机”。
3. **尽快保存磁盘镜像及可用快照。** 快照可辅助保护，但不要默认它独立于已失陷的管理权限，也不能代替全部取证工作。避免原盘写入、重装和就地修复。
4. **建立原件、分析副本和输出目录。** 对关键证据记录 SHA-256、路径、大小、采集时间、操作者及工具版本。所有试解、修复和恢复输出写到独立位置。
5. **保存时间线。** 记录首次异常、最后正常备份、发现时间、隔离、关机、重装、扫描和实验时间，并注明时区与可能的系统时钟偏差。

重装、日志轮转及后续写入可能覆盖关键证据，应将现场保全列入恢复业务之前的明确步骤。如果必须紧急重建，优先在新环境恢复服务，尽可能留下旧盘和旧系统供分析。

## 4. 第二阶段：找到并保存勒索信息与执行痕迹

勒索信可能存在于数据目录或其他账户目录。应扩大查找范围，不要仅凭桌面没有弹窗就判断没有联系方式。

重点位置包括加密文件所在目录、原始源目录、磁盘根目录、所有账户的桌面与文档、Public、临时目录、ProgramData、AppData、回收站和安全软件隔离记录。文件名称可包含 RECOVERY、RESTORE、DECRYPT、README、HELP，也可能完全不同。

找到后保存原文件、原路径、时间戳与哈希，截图作为补充。邮箱、网址、受害者 ID、报价及对话分别留档；按警方要求统一联系，避免多人重复沟通或自行提交敏感业务样本。

同步保全这些线索：

- SQL Server 错误日志、已有登录审计、SQL Server Agent 作业及历史；默认日志并不记录全部 SQL。
- Windows 安全日志、PowerShell 日志、计划任务、服务、远控软件日志与安全产品告警；可见范围取决于事前配置和保留策略。
- 投毒脚本、载荷、下载地址、进程命令行及文件哈希；保留可疑程序，不直接执行。
- Amcache、Prefetch 等系统痕迹，可辅助建立程序存在或运行活动的时间线。Amcache 不是所有程序执行的完整清单，条目存在也不能单独证明执行。

## 5. 第三阶段：同时评估四条恢复路线

### 5.1 找到未受影响的副本

优先检查离线备份、云端历史版本、存储快照、备份仓库保留点、异地主机及可用数据库副本。先保护它们，防止同步覆盖或进一步删除。事务日志通常需要配合适用的基础备份和连续恢复链，不能把“有日志”视为必然可恢复。

### 5.2 按误删恢复思路寻找旧内容

有些程序采用“生成加密副本，再删除原件”，可能留下可恢复的旧文件；原地覆盖加密则不会自动留下完整原件。还可以查找旧备份、临时副本、被删除文件及未分配空间。

此路线高度依赖覆盖情况、SSD TRIM、存储回收机制和后续写入。应尽早镜像，在副本上扫描，恢复结果写到其他介质。对仍在线写入的源盘直接运行恢复软件，可能覆盖待救数据。

### 5.3 验证已知解密工具或实现缺陷

按勒索信、样本哈希、文件尾部、区段规律和攻击时间匹配具体变种，再使用官方工具在副本上测试。

对历史漏洞、弱随机数／密钥生成及跨文件复用等方向，应留下实验记录：假设、输入哈希、工具和版本、搜索空间、耗时、结果及验证方式。运行中的进度信息不能代替最终结果，单次未命中也不能排除所有实现缺陷。

例如 Gen 在 2024 年发布的 Mallox 解密工具针对特定早期版本，研究说明该缺陷约在 2024 年 3 月被修复。这个时间界限描述的是该工具与该缺陷，不是所有同名家族、平台或后续工具的统一结论，见[原始研究](https://www.gendigital.com/blog/insights/research/decrypted-mallox-ransomware)。

ChaCha20 本身不是“弱密钥算法”。通常值得验证的是生成过程是否可预测、随机数种子空间是否过小、key/nonce 是否错误复用等实现问题。没有这些证据，对正确生成的完整密钥做穷举没有现实意义。

### 5.4 从完好数据库结构中抢救记录

对于无法解密的局部损坏，可尝试从有效数据页提取记录，导入新库。先检查原 MDF/NDF 是否存在且损坏更轻；若只有备份，则需先解析备份流。

```text
备份副本 → 识别容器、备份集及压缩方式 → 定位数据流
        → 标记受损范围 → 校验完好页 → 按表结构提取记录
        → 导入隔离新库 → 完整性检查与业务对账
```

不能把备份改名成 MDF，也不能删除加密区后拼接剩余字节。备份压缩、数据库页压缩、大字段、跨页记录及元数据损坏都可能增加提取难度；压缩备份不适合直接按物理文件每 8KiB 扫描数据库页。

先用兼容版本的隔离 SQL Server 对副本运行 `RESTORE HEADERONLY`、`RESTORE FILELISTONLY`、`RESTORE VERIFYONLY`，保存完整输出；具备条件时尝试还原到新库、新路径。`VERIFYONLY` 不验证备份中数据的全部结构，通过不等于完整性成立，见[微软说明](https://learn.microsoft.com/en-us/sql/t-sql/statements/restore-statements-verifyonly-transact-sql)。

优先选一张有准确表定义、业务可核对的关键表进行验证，再扩大范围。不要在唯一原件上运行 `REPAIR_ALLOW_DATA_LOSS`；它可能删除受损内容，并不解密数据。

## 6. 文件分析方法与容易误判的地方

| 方法 | 用途 | 限制 |
| --- | --- | --- |
| 熵扫描 | 发现统计特征变化，提出区段和周期假设 | 压缩数据也高熵；固定单字节 XOR 不改变香农熵 |
| 精确明密文对比 | 确认改动位置、长度、附加和截断 | 同名同版本 DLL 未必字节一致；相邻日期备份不是精确原件 |
| 结构解析 | 验证 MTF 描述符、流边界、页结构 | 找到字符串不等于解析通过；需要上下文连续性 |
| 跨文件尾部比较 | 区分固定标记与变化参数 | 不能仅凭不同字节宣布密钥独立随机 |
| 已知明文测试 | 验证简单 XOR、密钥流复用等假设 | 正确实现的现代密码不会因此自动泄露密钥 |
| 数据库与业务校验 | 检查提取结果是否可用 | 能读取、能导入、记录完整、业务一致是不同层次 |

对 ChaCha20 等直接以密钥流异或的形式，可以由精确明密文对计算对应位置的密钥流：

$$
S=P\oplus C
$$

只有其他文件使用同一段密钥流且正确对齐时，才能借此恢复对应区段；恢复的是密钥流，不是自动获得原始密钥。相同 key 但不同 nonce 通常也会产生不同密钥流。

测试时必须剔除未加密区域，因为它们的异或结果均为零；也要核对文件偏移与加密器计数器的关系。不同日期的备份即便业务内容相似，其记录位置和备份布局也可能变化，不能据“大量差异”直接排除所有复用可能。

## 7. 恢复上线与长期改进

恢复验收应分别回答：文件是否还原、数据库是否可用、业务数据是否可信、运行环境是否干净。

- 在干净隔离环境验证解密器和输出，随后做实际还原、`DBCC CHECKDB` 及应用验证。数据库检查通过也不代表业务时间范围和记录数量没有缺失。
- 按业务优先级核对关键主数据、交易记录及关联关系；统计缺失日期、记录数、主键重复及关联缺失，注明抢救数据的不确定性。
- 修复入口、排查持久化，并从可信设备轮换可能泄露的数据库、系统、域及备份凭据。文件恢复不代表攻击者访问已被清除，也不能证明没有数据外传。
- 建立生产与备份的权限隔离，保留离线或不可变副本；针对加密覆盖、误删及整机失陷实际演练恢复，明确可接受的数据丢失量和恢复时长。
- 将关键日志集中保存到受害主机难以修改的位置；准备镜像空间、采集工具、恢复环境和警方／服务方联系方式。

## 8. 可直接使用的处置清单

1. 隔离网络与备份访问，评估本机是否仍在加密，记录首个时间点。
2. 保护易失证据，保存磁盘与关键日志，避免先重装覆盖现场。
3. 查找并保存勒索信、联系方式、原路径和受害者标识，按警方要求统一联系。
4. 清点所有数据和备份副本，优先锁定未受影响的恢复点。
5. 尽早评估误删／旧副本恢复机会，避免后续写入覆盖。
6. 用副本确认格式、压缩方式、加密区间与尾部元数据，形成可复核记录。
7. 有依据地匹配官方解密工具、历史漏洞及密钥生成缺陷，限定实验范围。
8. 对未加密数据先做一张关键表的提取和业务验证，再决定批量抢救。
9. 在干净环境恢复、对账、修复入口、轮换凭据后上线；继续保存原始证据与实验记录。

处置时应尽早保留恢复机会：现场、联系方式、未覆盖的旧数据、独立备份和精确样本都可能在后续发挥作用。算法分析只是其中一条路线，是否值得继续投入，应由可验证证据决定。
