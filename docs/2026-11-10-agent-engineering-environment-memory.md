# Agent 工程2：从工作环境到记忆设计

阅读日期：2026-11-10（America/Anchorage）。从如何管理 Coding Agent 读到如何设计记忆，今天的讨论逐渐落在一个问题上：当模型越来越强，人应该准备什么，又应该把哪些决定交给模型？

## 二、从管理 Agent，到准备它工作的环境

第一篇讨论如何把任务交出去：说明目标、约束和成功标准，让 Agent 自行验证，人保留产品取舍与最终交付判断。生成代码和通过测试，都不能回答“这项修改是否值得存在”。并行 Agent 还会增加协调、审查和上下文切换成本，产出数量不等于生产力。

第二篇讨论交付任务之前该准备什么：准确的文档、可查询的状态、可操作的工具，以及清楚的权限边界。环境中可以直接查到的信息不必反复抄入记忆；真正需要留下的是决策原因、特殊约束和经过验证的经验。

例如，数据库 Agent 可以从监控查询当前磁盘使用率，从配置读取现行参数；“为什么这家客户不能在白天重启”“上次为什么放弃某种优化”，则需要额外保存。前者改善工具与可观测性，后者沉淀背景与判断。这里所说的环境，既包括工具和运行设施，也包括可发现、可维护的知识。

两篇合起来，可以理解为：**把目标说清，把环境建好，让结果可验证，再把值得继承的经验留下来。**

## 三、记忆如何从经历变成知识

Anthropic 原文最值得关注的，是一套让记忆持续演化的机制：任务执行中先捕捉值得保留的经验，再利用任务之间的时间，回看记录、纠正错误、重新组织知识。它借用了人类睡眠中巩固记忆的类比，把后一个过程称为 **dreaming（做梦）**。

### 一边做事，一边判断什么值得记

任务进行时写下笔记，可以让这次发现的规律在后续会话中继续使用。但把所有见闻都记下来，会把不断变化的状态复制成很快失效的旧版本，也会让整理笔记挤占实际工作的时间。

宝可梦实验呈现了这种差别：屏幕已经显示的钱数和位置可以随时重读，策略、计划和摸索出的规则却需要主动保存。这里的关键是选择信息，而非追求笔记数量。模型写下某条经验，其实也在预测未来会需要什么。

### “做梦”：回到经历里，修正已经形成的认识

执行任务时，Agent 的注意力放在下一步行动上，可能匆忙写下错误结论。Dreaming 把整理工作放到单独的离线或后台阶段，让模型对照原始会话记录审视已有记忆：哪些说法有依据，哪些是误判，哪些已经过时。

原文中，Agent 错记了月见山附近一个地标的方位，后续不断相信这条记忆，反复走回原路。Dreaming 回查会话记录后改正方位，后续运行才走通路线。这个例子说明，记忆既可能帮助行动，也可能让错误跨会话延续；纠错需要能够追溯的证据。

这个过程使用上下文与外部存储，不涉及更新模型权重。它也不限于修正笔记：还可以跨会话寻找共性、合并重复内容、补齐缺页和修复链接，让一次任务的零散经历逐渐成为可复用的知识。

### 从原始记录到 Wiki，再到会话入口

原文给出的记忆结构可以理解为四层：

| 层次 | 作用 |
| --- | --- |
| 原始会话记录 | 保存经历，供检索和回查。 |
| 记忆笔记 | 提取当时认为重要的经验、计划和规则。 |
| Wiki 等知识组织 | 将分散的信息按主题串联，建立可导航的关系。 |
| 注入新会话的上下文 | 放置少量重要信息与索引，让模型知道去哪里继续查。 |

Dreaming 可以在这些层次之间整理和移动信息。频繁需要的知识可以进入会话入口，细节则留在下层按需读取。这样既减少每次重新发现知识的成本，也避免把全部历史塞进上下文。

Wiki 的价值在于帮助模型跨材料建立联系，原始搜索则保留核查细节的能力。二者结合可能更好；如果问题只需查一份文件，额外建 Wiki 也可能不划算。原文甚至出现 Wiki 比原始材料更大的情况：整理产生了更多文字，却没有形成有效抽象。

### 实验支持到哪里

回头核对中文文章，主要数据基本准确，但需要连同任务范围一起理解：

| 实验 | 结果与适用范围 |
| --- | --- |
| 宝可梦记忆量与进度 | Sonnet 3.7：413 个文件、977,930 字符、1 枚徽章；Fable 5：9 个文件另加 `global.md`，合计 10 个文件、43,406 字符、4 枚徽章。各比较一次运行，不能隔离模型能力差异。 |
| CL-Bench | 数据库子任务中，Opus 5.5 从 0.655 升至 0.838，Sonnet 4.6 从 0.330 升至 0.364；不是整个基准的综合结论。 |
| 指导的作用 | Sonnet 4.6 加入针对性指导后升至 0.641；“只记录失败”的限制则削弱了部分模型的记忆收益。 |
| 搜索与 Wiki | 内部文档实验含 25 道题：仅搜索 53%、仅 Wiki 最好 48%、组合最好 61%，组合每题约省 2 万 token。百分比是评分标准满足率。 |
| 构建成本 | Wiki 实验规模达到 128M dreaming token；“几千次提问才能回本”属于中文作者估算。 |

合同任务还暴露了一个具体问题：多个 Agent 同时写入同一张表，彼此覆盖内容，摘要也遗漏了重要条款。改为每份合同由单个 Agent 维护独立页面，并逐字保留条款后，生成的简报从覆盖 41/57 项事实，改善到可满足全部 57 项评分标准。这是特定任务中的信息覆盖改善，不能理解成法律任务的普遍准确率达到 100%。

这些实验共同说明，自主选择信息、任务指导和组织方式都可能影响结果；“规则越少越好”不足以概括原文。

### 从记忆机制到环境与壁垒

“记忆是环境的补集”抓住了减少重复记录的方向。把它继续推到“Agent 没有壁垒”“记忆框架没有未来”“记忆终局是数据库”，则进入了中文作者自己的技术与商业判断。实验能够帮助我们选择记忆策略，还不足以决定哪一类产品拥有长期壁垒。

## 四、让顶尖 LLM 自己设计记忆系统，合理吗？

今天进一步讨论的问题是：既然强模型更善于判断什么值得记，能不能干脆让它自己设计记忆系统？

**可以，而且值得尝试。关键是让设计接受任务结果的检验。** 以下是本次讨论形成的工程判断。

| 层次 | 自主决策内容 | 建议 |
| --- | --- | --- |
| 记忆内容 | 什么值得记、哪些猜测待验证、哪些内容该删 | 让模型承担主要判断，保留来源与纠错能力。 |
| 知识组织 | 如何分文件、建索引、链接与归纳 | 允许模型调整，用后续任务效果检验。 |
| 基础机制 | 存储、权限、版本、并发、恢复和预算 | 模型可以参与设计，由可执行机制落实保证。 |

前沿模型擅长语义理解，让它按任务选择信息，通常比人工预设大量分类更灵活。但“善于组织知识”与“保证系统可靠”是不同能力。即使方案由模型提出，持久化和权限检查仍需要实际执行与验证。

这并没有要求基础设施必须由人设计：模型也可以选择存储方案、编写版本管理和并发控制代码。需要区分的是设计者与验收依据。系统是否可靠，要通过实际行为判断，不能由设计它的模型自述保证。自主设计的收益与模型能力、任务类型和可用反馈有关，不能只凭“这是顶尖模型”就预先认定最优。

### 自主设计仍要面对什么

**了解当前任务，不等于知道未来需求。** 记忆是在预测未来的信息价值，模型也会遗漏。保留适当的原始证据与检索入口，可以让后续会话找回未被摘要保留的信息；日志本身也受工具可观测性限制，不能被视为现实的完整记录。

**能够纠错，不等于不会自我强化。** 同一模型写下猜测，下次可能把它当成事实。有效复核应回到证据，区分观察、推断和已验证规则；仅要求模型“再想一遍”并不提供新的依据。

**少设死规则，不等于没有约束。** “只许记失败”限制信息选择；“说明来源”“不要覆盖其他任务的写入”“保留关键合同条款”服务于正确性。是否有效取决于具体模型和任务，需要验证。

此外，整理记忆也会争夺执行任务的时间。离线整理把成本转移到后台，却不会消除成本；应看长期任务收益，而非笔记是否工整。

### 为什么这仍然需要系统设计

“强模型能自主组织记忆”不能推出“记忆框架没有价值”。框架可以减少对知识结构的预设，同时提供可靠存储、权限隔离、共享、审计与恢复。框架应当承担哪些职责，仍需按场景判断。

同样，完善环境可以减少额外记忆的负担。若把决策理由也维护进项目 Wiki，它便成为共享环境的一部分；若尚未沉淀，就可能只能从会话记录里找。环境与记忆可以相互转化，“补集”更适合作为减少冗余的提醒，而非严格的集合定义。

## 五、对日常工作的启发

1. **现行状态就近查询。** 参数、指标和代码行为优先读取当前来源，避免复制后漂移。
2. **保存不可还原的理由。** 记录目标、取舍、特殊约束和失败经验，并关联证据。
3. **入口保持简短。** 用索引指向细节，不把全部知识强行注入每次会话。
4. **让组织方式可演化。** 允许模型增删结构，同时保留版本、核验和恢复能力。
5. **按结果评估。** 观察正确率、完成时间、检索与维护成本、错误复用率；文件更少或结构更复杂都不是成功标准。

还需继续验证：模型自组织在哪些任务上优于人工结构？何时值得建 Wiki？如何发现记忆过时？模型升级后哪些旧规则应删除？

当前判断是：**模型越强，越值得减少对其知识组织方式的预设；同时保留清楚的目标、可靠的基础机制与外部验证。**
