# LLM 隐私推理：全链路架构、硬件隔离与工程代价

目前工业界落地的**生产级 LLM 隐私推理**（如 Apple Private Cloud Compute、Tinfoil、Azure/GCP Confidential GPU 等），核心路线是**基于硬件 TEE（可信执行环境，机密计算）的全链路加密与远程证明**。

> 注：纯密码学路线（全同态加密 FHE、多方安全计算 MPC）虽然无需信任硬件厂商，但目前在百亿/千亿参数 LLM 上的计算与通信开销高出 $10^3\text{–}10^5$ 倍，尚未达到通用生产可用状态。下文聚焦当前主流的 **TEE 全链路方案**。

---

## 一、 怎么做到“全链路”隐私？

传统云端 LLM 推理中，HTTPS 只保传输；流量一到云厂商的负载均衡器（LB）就完成了 **TLS 终止**，Prompt、用户 IP、响应内容在网关、宿主机内存、GPU 显存和日志里全是明文。

全链路隐私推理的目标是：**除用户端和经过验证的硬件安全飞地（Enclave）内部外，链路上任何节点（网络运营商、云厂商、Hypervisor、运维人员）都只能看到密文，且无法将“用户身份”与“请求内容”关联。**

典型请求生命周期如下：

1. **远程证明（Remote Attestation）与验签**
   - 客户端在发送 Prompt 前，先向目标推理节点索要**硬件签名的证明报告**（包含 CPU/GPU 芯片厂商烧录的硬件信任根签名 + 当前运行的 OS/容器/推理引擎镜像哈希）。
   - 客户端将该哈希与公开的**透明度日志**（Transparency Log）比对，确认远端跑的是经过审计、无后门、无日志落盘的合法代码，并拿到该飞地内生成的临时公钥。
2. **端到端加密 + 匿名中继（防内容泄露 & 防身份关联）**
   - 客户端用飞地公钥（通常基于 **HPKE / OHTTP**，或将 TLS 直接终止在飞地内）加密 Prompt。
   - 若要防“谁问了什么”（元数据分析），请求先发给第三方 **OHTTP Relay（匿名中继）**：中继看到用户 IP 但解不开密文；中继剥离 IP 后转发给云端网关，云端看到密文但不知道用户是谁。
3. **网关透传与飞地内解密**
   - 云端负载均衡器只做外层传输转发，**无法解密内层载荷**。密文直达受保护的机密虚拟机（CVM / Enclave）内部，才在加密内存中完成解密。
4. **CPU TEE → 总线 → GPU TEE 安全推理**
   - Prompt 在 CPU 加密内存中完成分词（Tokenization），随后通过加密通道（PCIe Bounce Buffer / TEE-I/O）送入处于机密计算模式的 GPU 显存。
   - 多卡并行（TP/PP）时，中间激活值和 KV Cache 通过加密互联（如 Blackwell 原生加密 NVLink）在卡间流转，全程不以明文暴露在物理内存或总线上。
5. **无状态销毁与密文返回**
   - 生成的 Token 在飞地内加密后返回客户端。
   - 请求结束后，Prompt 与 KV Cache 仅存于易失性内存（RAM/VRAM），**不落盘、不记录明文日志**，并立即擦除。

## 二、 飞地与远程证明：信任是如何建立的？

全链路隐私的前提，是客户端在发送 Prompt 前能确信：**远端确实运行在真正的 TEE 硬件中，且跑的是未经篡改、无日志后门的代码**。TLS 只证明“域名身份”，而**飞地**（Enclave / CVM）与**远程证明**（Remote Attestation, RA）证明的是“执行环境与代码完整性”。

### 1. 飞地与四方角色边界

**飞地**（如基于 Intel TDX / AMD SEV-SNP 的机密虚拟机 CVM，配合处于 CC Mode 的 GPU）是一块由硬件内存控制器实时加密隔离的执行环境，宿主机 OS、Hypervisor 与运维人员均无法读写其加密内存。

理解远程证明的关键，是区分四个角色的信任关系：

| 角色 | 信任状态 | 核心职责 |
| :--- | :--- | :--- |
| **宿主机 / 云厂商** | **不可信** | 提供物理资源与网络转发，可能试图篡改镜像、窥探内存或劫持流量 |
| **飞地（CVM 内程序）** | **验证前不可信** | 负责生成临时密钥、运行推理引擎，并主动向硬件**申请开具证明报告** |
| **CPU/GPU 安全硬件** | **信任根（可信）** | 芯片内独立安全协处理器，全程监控启动、记录真实哈希，充当**绝不撒谎的“公证处”** |
| **客户端** | 验证方 | 核验硬件签章真伪与证明内容，决定是否放行并发送加密 Prompt |

> 即使云厂商启动了一个带后门的**恶意飞地**，该飞地依然可以调用硬件接口申请签名，但硬件只会从只读寄存器里如实签出它被篡改后的哈希——相当于签发了一份“自首书”，客户端比对后直接拒连。

### 2. 为什么硬件签名不可操控？

* **硅片信任根与物理隔离**：芯片出厂时将唯一根私钥烧录在熔丝（eFuse）或由物理不可克隆函数（PUF）生成，电路布线上仅连通片上独立安全核（如 AMD-SP、Intel SEAM/TDX Module、NVIDIA GPU RoT），主 CPU 核、GPU 计算核与宿主机完全没有访问通路。同时，片上不可修改的掩膜 Boot ROM 校验固件签名并强制防回滚（TCB 版本号）。
* **启动度量链（Measured Boot）**：从开机起，硬件与底层固件逐级计算各层组件的密码学哈希，并单向扩展（Extend）至硬件只读度量寄存器（如 TDX 的 `MRTD`/`RTMR`、SEV-SNP 的 `MEASUREMENT`）：

$$
R_{\text{new}} = \text{Hash}(R_{\text{old}} \,\|\, \text{Hash}(\text{Component}))
$$

* **推理程序的锁死时机**：推理引擎、OS 及编译好的 CUDA Kernel 二进制代码（`.cubin`/`.so`）封装在只读镜像中，通过 `dm-verity`（块级 Merkle Tree）挂载，其根哈希在 **CPU 侧启动链阶段** 就已锚定进度量寄存器。任何 1 bit 篡改都会导致读取校验失败或度量值彻底改变。

### 3. 远程证明流程与密钥绑定

硬件签发的证明报告（Quote）由**硬件自填区**（度量值、Debug 开关、TCB 固件版本，软件不可写）与 **64 字节软件可填区（`UserData` / `ReportData`）** 拼装而成：

1. **发起挑战**：客户端生成随机 `Nonce`（防重放攻击），发往远端节点。
2. **飞地内生密钥并请求盖章**：飞地在加密内存内生成临时密钥对 $(pk_{\text{enclave}}, sk_{\text{enclave}})$（私钥永不出飞地），计算 $\text{Hash}(\text{Nonce} \,\|\, pk_{\text{enclave}})$ 填入 `UserData`，调用硬件专用指令（如 `TDCALL` / `/dev/sev-guest`）请求签名。硬件通过底层隔离通道识别调用者身份，将该飞地专属的真实度量值与 `UserData` 绑定签名。
3. **客户端四重核验**：
   * **验签名与证书链**：确认由芯片厂商合法芯片签发且未被吊销；
   * **验 TCB 状态**：确认非 Debug 模式，微码与固件无已知致命漏洞；
   * **验新鲜度与公钥绑定**：核对 `UserData` 中的 `Nonce` 与 $pk_{\text{enclave}}$，防止恶意网关拿真飞地报告搭配假公钥做中间人掉包；
   * **验度量值**：确认镜像哈希属于已审计的合法版本。

验证通过后，客户端即可确认“只有跑着这份合法代码的真 TEE 硬件内部才持有解密私钥”，进而用 $pk_{\text{enclave}}$ 建立端到端加密通道。

### 4. LLM 场景下的工程闭环

* **从哈希到“代码可信”**：单纯一串哈希无法证明代码无后门，必须配合**可复现构建（Reproducible Builds）**与**公开透明度日志（Transparency Log）**——外部可拉取源码复现出逐比特一致的哈希；服务商无法在不留痕的情况下向特定用户下发定向后门镜像。
* **CPU + GPU 复合证明与信任传递**：GPU 硬件通过 SPDM 协议证明自身已开启 CC Mode、固件合规且显存加密生效，并与 CPU 飞地建立加密总线绑定。GPU 无需在每次加载 CUDA Kernel 时重复证明，而是通过“可信 CPU 飞地 $\rightarrow$ 加密 PCIe/SPDM 通道 $\rightarrow$ 可信 CC GPU”完成信任传递。
* **百 GB 级模型权重与握手开销优化**：大模型权重不塞入开机度量，而是在飞地通过证明后，由 **KMS/KBS 校验 Quote 并下发权重解密密钥**，加载时按分片/Merkle Tree 校验完整性；客户端侧通常采用本地缓存证书链与吊销列表，或 **Passport 模式**（由独立 Verifier 签发短期有效凭证），以降低每次请求的验签延迟与元数据暴露。

## 三、 哪些组件（硬件与软件）要参与？

全链路需要**从端到芯、软硬协同**，缺一环就可能出现明文“断点”：

| 层级 | 参与组件 | 典型实现 | 核心职责 |
| :--- | :--- | :--- | :--- |
| **客户端** | 客户端 SDK / OS 安全组件 | Apple 设备 / 浏览器或本地验证代理 | 验证远端硬件证明报告、核对透明度日志、执行端到端加密 |
| **网络匿名层** | 匿名中继（可选但高隐私必备） | OHTTP Relay（RFC 9458，如 Cloudflare 托管） | 切断客户端 IP 与请求内容的关联 |
| **边界网络层** | 负载均衡 / API 网关 | 普通 L4/L7 代理 | 仅透传密文流量，**不持有**应用层解密私钥 |
| **CPU 与内存** | **CPU TEE（硬件）** | Intel TDX、AMD SEV-SNP、Apple Silicon Secure Enclave | 硬件级内存实时加密，隔离 Hypervisor 与宿主机 OS |
| **总线与 I/O** | **PCIe / TEE-I/O（硬件）** | PCIe IDE / DMA 加密通道、Bounce Buffer | 防止通过物理探针或恶意宿主机 DMA 窃取 CPU-GPU 传输数据 |
| **算力核心** | **GPU TEE（硬件）** | NVIDIA Hopper (H100/H200) / Blackwell (B200) CC Mode、Apple 定制服务器芯片 | 保护显存中的模型权重、Prompt、激活值与 KV Cache |
| **多卡互联** | **高速互联加密（硬件）** | Blackwell 原生加密 NVLink / NVSwitch（Hopper 需整机直通 PPCIE） | 防止跨卡张量并行通信在总线上被嗅探 |
| **信任基础设施** | 证明服务 & 密钥管理（软件） | 芯片厂商证明服务、KMS/KBS、公开透明度日志 | 校验硬件证书链、按证明结果释放模型权重解密密钥 |
| **推理运行时** | 硬化 OS & CC 适配推理引擎 | 裁剪版无 SSH OS（如 PCC OS）+ 适配版 vLLM / TRT-LLM / SGLang | 禁用运维后门与明文日志，适配异步加密流与内存清理 |

## 四、 这些组件要“硬隔离”吗？

需要分两个维度回答：**“隐私 vs 非隐私业务隔离”** 和 **“隐私用户之间的隔离”**。

### 1. 与非隐私推理的隔离：GPU 必须硬隔离，通常做到整机/集群隔离
* **单张 GPU 内：绝对不能混跑**
  * 以 NVIDIA H100/B200 为例，开启机密计算（**CC Mode**）是**整卡级别的硬件模式切换**（需要重置/启动时配置）。
  * **CC Mode 与 MIG（多实例 GPU 硬件切分）互斥**，无法把一张卡切成几份，一份跑普通推理、一份跑隐私推理。
* **单台多卡服务器内：受限于互联拓扑，大多整机隔离**
  * **Hopper (H100/H200)**：如果要跑多卡并行（PPCIE 模式），需要把整台机器的所有 GPU 和 NVSwitch 全部直通给同一个 CVM，不能在同机混跑普通 GPU 任务。
  * **Blackwell (B200)**：引入了原生 NVLink 硬件加密，节点内隔离粒度更灵活，但单张物理卡依然只能二选一（全卡 CC 或全卡普通）。
  * **CPU 宿主机层**：理论上 TDX/SEV-SNP 允许同一台宿主机跑普通 VM 和机密 VM，但为了防 CPU 缓存/分支预测等微架构侧信道以及满足合规审计，高安全方案（如 Apple PCC）会直接采用**物理专用的隐私推理集群**，不参与任何非隐私推理。

### 2. 多用户（租户）之间的隔离：共享硬件，但状态与缓存必须强隔离
* **不需要“一用户一卡/一 VM”**：那样成本和冷启动延迟完全不可接受。生产中，**多个隐私用户的请求通常共享同一个已通过证明的 CVM + Confidential GPU 集群**。
* **必须隔离的软件/状态边界**：
  1. **会话无状态（Stateless）**：请求处理完立即清空显存和内存中的上下文，不留痕迹。
  2. **KV Cache / Prefix Caching 强隔离（极关键）**：现代推理引擎普遍开启跨请求 Prefix Caching 来降低首字延迟（TTFT）。但如果多个用户共享全局 Prefix Cache，攻击者可以通过构造探测 Prompt 并测量 TTFT 耗时（缓存命中快、未命中慢），逐 Token 还原其他用户的私有 Prompt（如 *PROMPTPEEK*、*EarlyBird* 攻击）。因此隐私推理中必须**彻底禁用跨用户 Prefix Caching**，或引入**基于租户密钥加盐的隔离缓存**（仅允许同一用户多轮对话复用）。
  3. **Batching（混批）隔离权衡**：Continuous Batching 下，不同用户的请求混在同一个 Batch 中计算，理论上存在显存带宽竞争导致的微弱时序侧信道。极高安全场景会采用分池批处理（Partitioned Batching）或注入虚拟填充（Padding），但多数商业方案会接受共享 Batching，把防御重心放在隔离宿主机和隔离 KV Cache 上。

## 五、 代价有哪些？

### 1. 性能与延迟代价
* **框架适配决定下限**：
  * 如果直接在 CC 模式下跑未做适配的推理框架（Eager Mode），每次 Kernel 下发和 CPU-GPU 同步都要走加密指令通道与 Bounce Buffer 拷贝，吞吐可能暴跌 **30%~40%**，低并发延迟甚至翻倍。
  * 经过 **CC-Aware 适配并启用 CUDA Graphs**（把大量小指令打包一次性提交）后，纯推理算力损耗可压缩到 **1%~3%**（Blackwell 实测多卡 TP4/TP8 仅损失约 1.5%~3%）。
* **多卡扩展瓶颈（代际差异明显）**：Hopper 缺乏硬件原生 NVLink 加密，跨卡扩展受限；要低损耗跑超大参数模型，几乎强依赖 **Blackwell** 这一代具备硬件 NVLink 加密的架构。
* **禁用跨用户缓存的隐性算力代价**：对于长 System Prompt、共享文档 RAG 场景，禁用跨用户 Prefix Caching 会导致大量重复 Prefill 计算，显著拉高 TTFT 和单 Token 推理成本。
* **网络额外跳数**：若启用 OHTTP 匿名中继，会增加一次中继转发的网络 RTT；首次连接还有远程证明和密钥协商的握手延迟。

### 2. 硬件与资源利用率代价
* **无法混部与超卖**：由于不能与非隐私业务混跑且不支持 MIG 切分，隐私推理集群只能独占资源池。业务波谷时，闲置 GPU 无法像普通集群那样弹性切给离线批处理或普通推理，**资源利用率下降、单次推理成本上升**。
* **硬件门槛高**：旧卡（如 A100）不支持 GPU CC；必须采购支持 TDX/SEV-SNP 的服务器 CPU + H100/H200/B200 或定制芯片。

### 3. 研发与“盲运维”代价（工程落地最痛的部分）
* **极难排障**：为了向用户证明“运维看不到数据”，生产节点必须砍掉 SSH 登录、交互式 Shell、明文日志和内存 Dump。一旦线上出现 OOM、死锁或推理异常，排查成本极高，需要建设脱敏结构化遥测和离线复现环境（如 Apple 的 VRE）。
* **供应链与发版复杂度**：所有运行在飞地内的镜像必须做到**可复现构建**（Reproducible Builds）并写入公开透明度日志；每次模型更新或引擎升级都要走完整的签名、上链和客户端校验流程。

### 4. 残余安全边界（并非绝对无懈可击）
* **信任根转移**：从“信任云厂商/模型服务商”转移为“信任芯片厂商（NVIDIA / Intel / AMD / Apple）的硬件设计与供应链”，以及相信其固件无致命漏洞。
* **流量侧信道残留**：即使内容全加密，网络观察者仍可能通过密文包大小、流式返回的 Token 数量和生成间隔推断部分信息；若要彻底抹平（如固定长度填充 + 恒定速率发包），带宽和延迟代价会成倍放大。
