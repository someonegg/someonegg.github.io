## 1. Paxos 解决什么问题

Paxos 是一个分布式共识算法。

目标是让多个节点对同一个值达成一致。

例如：

```text
slot5 = ?
```

最终决定：

```text
slot5 = X
```

并保证：

```text
永远不会出现
slot5 = Y
```

---

## 2. Single Paxos

### 角色

Single Paxos 里通常有三类角色：

```text
Proposer
    发起提议
    负责发送 Prepare / Accept

Acceptor
    对提议投票
    负责记录承诺和已接受的值

Learner
    学习最终被多数派接受的结果
```

核心安全性主要依赖 Acceptor 保存的状态。

### 核心流程

Single Paxos 为一个 slot 选择一个不可再改变的值。

流程分为两个阶段：

```text
Phase 1：Prepare / Promise
Phase 2：Accept / Accepted
```

其中：

```text
n = Proposal Number
value = 需要共识的数据
```

提议编号 `n` 需要全局唯一、全序可比较。工程上通常使用：

```text
(local_counter, node_id)
```

### Acceptor 保存的状态

```text
promised_n
    已承诺不再接受小于该编号的提议

accepted_n
    已接受的最高提议编号

accepted_value
    accepted_n 对应的值
```

这些状态需要持久化，避免节点重启后遗忘已经做出的承诺。

### Phase 1：Prepare / Promise

1. Proposer 选择一个更大的编号 `n`，发送：

```text
Prepare(n)
```

2. Acceptor 检查编号：

```text
if n >= promised_n:
    promised_n = n
    返回 Promise(n, accepted_n, accepted_value)
else:
    返回 Reject(promised_n)
```

3. Proposer 收到一个 Quorum 的 Promise 后选择 value：

```text
所有响应都没有 accepted_value：
    使用自己的 value

存在 accepted_value：
    使用 accepted_n 最大的响应所对应的 accepted_value
```

普通多数派配置中：

```text
Quorum = floor(N / 2) + 1
```

### Phase 2：Accept / Accepted

1. Proposer 发送：

```text
Accept(n, value)
```

2. Acceptor 检查编号并持久化状态：

```text
if n >= promised_n:
    promised_n = n
    accepted_n = n
    accepted_value = value
    返回 Accepted(n, value)
else:
    返回 Reject(promised_n)
```

3. 一个 Quorum 接受同一个提议后，value 成为 `Chosen`。Learner 随后学习这个结果。

### 两个关键边界

单个 Acceptor 可以在更高编号下接受另一个值：

```text
Accept(10, X)
Accept(20, Y)
```

若 `X` 已被一个 Quorum 接受，后续合法提议会通过 Phase 1 发现并继承 `X`。

少数派接受的值只会在后续 Promise Quorum 覆盖相关 Acceptor 时产生约束：

```text
A 接受了 X

后续 Quorum 包含 A：
    新 Proposer 可能需要继承 X

后续 Quorum 不包含 A：
    新 Proposer 看不到 X
```

因此：

```text
单个 Acceptor 的 accepted_value 可以改变
Chosen value 不会改变
```

### Single Paxos 的本质

对于一个 slot：

```text
slot5 = ?
```

最终写入：

```text
slot5 = X
```

之后：

```text
可以反复确认
可以反复恢复
但不能改成别的值
```

因此可以把 Single Paxos 理解成：

```text
Write Once Register
```

## 3. 为什么需要 Multi-Paxos

实际系统需要决定的是一串日志：

```text
slot1
slot2
slot3
...
```

例如：

```text
slot1 = set x=1
slot2 = set y=2
slot3 = delete z
```

因此：

```text
Multi-Paxos = 很多个 Single Paxos
```

---

## 4. slot 与 epoch

这是 Multi-Paxos 最重要的概念。

### slot

表示：

```text
日志位置
```

例如：

```text
slot1
slot2
slot3
```

类似于 Raft 的：

```text
log index
```

### epoch / ballot

表示：

```text
控制权版本号
```

例如：

```text
ballot = 100
```

表示：

```text
当前拥有编号100的提议权
```

类似于 Raft 的：

```text
term
```

### 一个重要公式

```text
slot = What
epoch = Who
```

即：

```text
slot 决定什么
epoch 谁有资格决定
```

---

## 5. 一个常见误区

很多人会理解成：

```text
epoch100 -> Leader=A
epoch200 -> Leader=B
epoch300 -> Leader=C
```

仿佛每个 epoch 都在共识：

```text
value = LeaderID
```

这个理解把 ballot 误当成了共识值。

Multi-Paxos 共识的仍然是：

```text
日志内容
```

例如：

```text
slot1 = cmd1
slot2 = cmd2
slot3 = cmd3
```

下面的 Leader 身份不属于共识值：

```text
Leader=A
```

例如：

```text
Accept(100, slot1, cmd1)
Accept(100, slot2, cmd2)
Accept(100, slot3, cmd3)
```

其中：

```text
100
```

它表示 ballot。

真正的 value 是：

```text
cmd1
cmd2
cmd3
```

---

## 6. Leader 是怎么来的

Paxos 理论里并没有：

```text
current_leader
```

这样的状态。

---

发生的是：

```text
Prepare(100)
```

成功后，多数节点记录：

```text
promised_ballot = 100
```

于是：

```text
<100
```

的提议全部失效。

---

结果近似变成：

```text
只有 ballot=100
能够继续提交日志
```

如果：

```text
ballot=100
属于 A
```

那么：

```text
A ≈ Leader
```

---

因此：

```text
Leader
来自控制权竞争的结果
```

---

## 7. Multi-Paxos 的优化

Single Paxos：

```text
slot1:
    Prepare
    Accept

slot2:
    Prepare
    Accept

slot3:
    Prepare
    Accept
```

每个 slot 都要执行一次 Prepare。

---

Multi-Paxos：

先执行一次：

```text
Prepare(100)
```

获得控制权。

然后：

```text
Accept(100, slot1)
Accept(100, slot2)
Accept(100, slot3)
Accept(100, slot4)
```

持续执行。

---

因此：

```text
Prepare
```

从：

```text
每条日志一次
```

变成：

```text
每次 Leader 切换一次
```

---

## 8. 什么情况下重新 Prepare

### Leader 故障

```text
Leader 挂掉
```

---

### 网络分区

```text
多数派联系不到 Leader
```

---

### Accept 被拒绝

收到：

```text
Reject
promised_n = 200
```

说明已经存在更大的 ballot。

---

此时必须重新竞争：

```text
Prepare(300)
```

---

## 9. Leader 切换如何恢复数据

假设：

```text
Accept(100, slot5, X)
```

已经被部分节点接受。

此时 Leader 崩溃。

---

新 Leader 发起：

```text
Prepare(200)
```

并收集多数派状态。

发现：

```text
slot5
曾经接受过 X
```

---

根据 Paxos 规则：

必须继续提议：

```text
Accept(200, slot5, X)
```

而不能提议：

```text
Accept(200, slot5, Y)
```

---

因此：

```text
已经决定的数据不会丢
可能已经被 chosen 的数据不会被覆盖
```

---

## 10. Prepare 回复什么

理论上的 Paxos：

```text
Promise(
    accepted_n,
    accepted_value
)
```

即：

```text
告诉新 Leader：

我接受过什么值
```

---

如果直接套用到 Multi-Paxos：

```text
slot1
slot2
...
slot1000000
```

全部返回。

显然不现实。

---

新 Leader 真正关心的是：

```text
日志尾部
```

即：

```text
Accepted
但尚未 Chosen
```

的部分。

---

通常节点维护：

```text
commit_index
last_log_index
snapshot
```

---

Prepare 回复更接近：

```text
Promise(
    ballot = 200,
    commit_index = 999990,
    last_log_index = 1000000,
    uncommitted_tail = [
        slot999991,
        ...
        slot1000000
    ]
)
```

---

如果已经有快照：

```text
snapshot@100000000
```

则只需传递：

```text
快照信息
+
快照之后的日志尾部
```

---

因此：

```text
理论 Paxos：
    返回所有 accepted value
工程 Multi-Paxos：
    返回未提交日志尾部
    + commit index
    + snapshot
```

---

Prepare 的核心目标是：

```text
告诉新 Leader：
哪些 slot
可能存在尚未完成的共识
```

---

## 11. 总结

```text
Single Paxos：
    对一个 slot 决定一个 value
Multi-Paxos：
    用一个 ballot 获得控制权
    对很多 slot 连续执行 Paxos
value 是日志内容（共识）
ballot 是控制权编号
Leader 是拥有最大 ballot 的节点
Prepare 的作用：
    获得控制权
    恢复未完成 slot
Accept 的作用：
    对日志达成共识
```
