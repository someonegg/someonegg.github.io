# 从读懂老项目到继承团队经验：AI 原生研发的三层工程

当 AI 已经能够快速生成大量代码，研发效率的瓶颈却没有随之消失。它只是换了位置：过去稀缺的是实现能力，现在更稀缺的是准确的上下文、可靠的执行边界，以及能够跨任务继承的经验。

这也解释了一个常见反差：同一个模型，在结构清晰的新项目里可以独立推进功能，进入一个运行多年的老项目后却频繁误判。它会读到已经废弃但仍有引用的代码，把半途而废的重构当作现行架构，从产品的一句模糊描述联想到错误模块，甚至在没有完成编译和运行验证时宣布任务结束。

问题不只是“模型不够聪明”。人与 AI 的真正差距，往往是人脑里保存着大量没有写入代码的隐含状态：哪些链路仍在生产运行，某个兼容分支为什么不能删除，哪套设计规范才是当前版本，以及此前哪些方案已经失败。

要让 AI 真正进入存量研发，至少需要完成三层工程：

1. 让项目本身变得可理解；
2. 让单次开发过程变得可执行、可验证；
3. 让一次任务的经验变成下一次任务可以安全继承的资产。

它们分别对应上下文工程、执行工程和记忆工程。三层缺一不可。

---

## 一、第一层：先让真实系统与它的描述一致

为老项目增加一份 `AGENTS.md` 是很好的起点，但它不是终点。如果项目中同时存在三套架构、两条废弃链路和大量未完成的设计，那么建立再详细的知识索引，也可能只是帮助 AI 更高效地理解混乱。

因此，上下文工程的第一步不是写更多文档，而是减少系统自身的歧义。

### 1. 清除“静态存在、运行时失效”的代码

静态引用只能证明某段代码可以被调用，不能证明生产流量真的会经过它。环境变量、灰度条件、废弃入口和迁移中的新旧链路，都可能让一段看起来完整的实现永远无法运行。

这类代码对 AI 尤其危险。模型通常会把仓库视为事实来源；当仓库本身同时保存多个互相矛盾的事实版本时，检索能力越强，误入歧途的机会反而越多。

治理目标应该是让“代码看起来怎样”尽量接近“系统实际怎样运行”。可以先由工具识别无引用代码和候选死链路，再结合运行数据、版本历史和业务人员的知识确认。AI 可以扩大排查范围，但不能仅凭静态分析决定删除。

### 2. 用减法降低状态空间

很多历史债务并非业务天然复杂，而是过度设计、迁移不彻底和多轮局部重构叠加的结果。每多保留一种消息机制、一套兼容协议或一个理论上可扩展的抽象，AI 和新成员就多面对一组可能的解释。

好的架构不在于表现得高级，而在于压缩理解和修改所需的状态空间。对于没有真实需求支撑的扩展点，与其继续为它补充说明，不如评估是否可以移除。上下文工程与架构简化因此存在正反馈：架构越收敛，需要解释的例外越少；例外越少，AI 的定位与修改越可靠。

### 3. 用分层索引代替一份巨型说明书

项目开始具备一致性后，可以建立跟随代码仓库演进的知识入口：

- 根目录 `AGENTS.md` 只保存项目级约束、知识索引和查找路径；
- 模块级 `AGENTS.md` 或 Wiki 保存领域背景、架构边界和局部规则；
- 更细的语义映射保存设计 Token、业务术语与工程 API 的对应关系；
- 对话中新出现的兼容性、排障和协作结论，就近写回相应模块。

这种结构的关键不在文件名，而在渐进式暴露：AI 先读取小而稳定的项目地图，命中模块后再展开细节，真正定位到文件后才读取源码。它避免每次任务都把整个知识库塞进上下文。

知识还必须接受漂移检测。模块新增、删除或大幅修改时，应提醒维护相应文档；否则一份过期 Wiki 比没有 Wiki 更危险。

## 二、第二层：把“开发需求”变成可校验的状态机

项目可理解，并不意味着 AI 会按工程规范完成需求。面对一句“按 PRD 改一下”，模型仍可能跳过范围确认，直接搜索和修改代码。

解决办法不是继续扩充提示词，而是把开发过程显式建模为有顺序、有产物、有退出条件的流水线。例如：

$$
设计收料
\rightarrow 需求拆解
\rightarrow 代码定位
\rightarrow 实现
\rightarrow 编译验证
\rightarrow 运行时验证
\rightarrow 知识沉淀
\rightarrow 提交
$$

后一阶段的输入必须来自前一阶段的产物。没有范围清单，就不能开始定位；没有编译成功的证据，就不能进入运行验证；没有验证结果，就不能声称完成。

### 1. LLM 做判断，脚本做确定性工作

这条分工几乎贯穿所有可靠的 Agent 工程：

- LLM 负责理解意图、解释需求、比较方案和诊断错误；
- 脚本负责精确搜索、批量下载、数值计算、幂等执行和结果检查。

例如，模型可以提出代码搜索词，但实际检索交给 `rg`；模型可以分析编译错误，但成功只能由退出码判断；模型可以解释视觉差异，但截图尺寸和像素阈值应由工具计算。

这不是削弱模型，而是让概率推理与确定性执行各自承担适合的职责。

### 2. 需求翻译必须保留依据

从产品语言到代码语言，中间至少存在范围、归宿、交互和命名四道鸿沟。

“页面出现一个红色提示条”在代码中可能叫 `TipsView`、`WarningBanner` 或某个协议字段。直接搜索中文通常没有结果，只搜索 `tips` 又可能命中数百处。更可靠的方法是结合模块地图、项目命名习惯、平台事件方法、业务同义词和跨模块通信方式，生成分层候选词，再用工具逐步收敛。

但语义扩展不能变成自由联想。对于“点击 X 后拦截并显示 Y”这样的行为，X、Y 和触发关系必须能追溯到设计稿标注、需求原文或用户指令。无法提供依据的联想，不应进入实现范围。

### 3. “完成”必须由外部证据定义

Agent 最常见的诚信问题不是故意撒谎，而是把局部完成误认为整体完成。代码已经生成，不等于能够编译；编译通过，不等于真实路径可用；页面能打开，也不等于视觉和交互符合要求。

因此验证至少要有两道闸门：

- 代码层：编译、静态检查、单元测试和有限轮次的自动修复；
- 运行层：装机或部署、真实路径操作、截图、日志以及视觉回归。

自动修复还需要硬上限。缺少符号、类型不匹配等局部错误可以尝试修复；构建配置、第三方链接或本次改动范围之外的问题应立即升级给人。无限重试只会让 AI 在错误方向上扩大改动。

最重要的是，成功证据要落盘：退出码、测试报告、截图、日志命中和验证结论，而不是依赖终端输出或模型的一句话总结。

## 三、第三层：把任务轨迹变成受治理的团队资产

一次需求顺利完成后，最容易丢失的并不是最终代码，而是形成代码的过程：为什么选择这个方案、哪些路径已经失败、哪些边界不能改变，以及如何验证结果。

单个项目可以用 `TECH_SPEC.md`、任务台账和时间线保存这些状态。但当任务跨越成员、Session、Agent、仓库和权限域时，仅靠项目文档还不够，需要进一步建设团队记忆。

团队记忆不是无限保存聊天，也不是给所有资料增加向量索引。它应当把任务中形成的背景、知识、代码关系和方法，转化为可检索、可组合、可追溯、可授权并可持续更新的资产。

这些资产大致可以分为四类：

| 资产 | 保存的状态 | 解决的问题 |
| --- | --- | --- |
| Chat Memory | 背景、约束、决定、失败路径 | 当时为什么这样判断 |
| Wiki | 架构、规范、Runbook、稳定事实 | 团队已经知道什么 |
| CodeGraph | 文件、符号、调用与影响路径 | 修改会影响哪里 |
| Skill | 步骤、工具、边界与验证规则 | 这类任务通常怎样完成 |

它们共同回答四个问题：发生过什么、团队知道什么、代码如何关联、通常怎样执行。

### 1. 抽象和证据必须同时存在

原始对话保真度高，但密度低；高级摘要易于使用，却可能在多轮压缩后失真。可行的记忆结构应同时保存：

- 原始对话、工单、代码和测试等证据；
- 从证据中提取的事实、约束和决定；
- 围绕项目或场景组织的高密度记忆；
- 少量稳定、低频更新的团队规则。

日常任务先读取上层摘要，需要核实时再回到原始证据。只有摘要没有证据，无法判断可信度；只有证据没有抽象，每次任务仍然需要从头阅读。

### 2. 权限与作用域先于相关性

团队环境中最危险的不是“没召回”，而是“召回了一条看似相似、实际上不适用的经验”。两个部署流程可能只有一个目录名不同，却分别属于生产和测试环境；两项修复可能修改同一个参数，方向却完全相反。

因此，检索顺序应该是：

$$
身份与 ACL
\rightarrow 项目、分支、路径和版本过滤
\rightarrow 固定规则绑定
\rightarrow 相关性召回
\rightarrow Token 预算内装配
$$

无权访问或作用域不符的资产不应进入候选池，而不是召回后再删除。语义相似只负责发现线索，不能证明经验可以直接执行。

### 3. 资产必须分级并拥有生命周期

TencentDB Agent Memory 的内部分析提供了一个很有价值的警告：在其报告的 22,361 条 canonical 关系中，只有 231 条被保留为强关系，绝大多数只能作为相关背景。这个结果不能直接推广到所有团队，却说明“有关联”与“可复用”之间隔着严格的证据、时序和适用性判断。

因此资产库不能只有保留和删除两个状态，而应至少区分：

- 可以进入计划和执行的强资产；
- 只用于提示风险的弱经验；
- 帮助理解背景、不能驱动操作的参考信息。

资产还需要支持 Review、发布、锁定、Fork、合并、降权、过期、撤回和删除。一次错误反馈必须改变后续路由，而不是期待下一个 Agent 自己识别同一条错误记忆。

## 四、三层之间如何形成闭环

上下文、执行和记忆不是三个独立系统。它们应形成一个持续收敛的循环：

$$
清理真实系统
\rightarrow 建立项目地图
\rightarrow 结构化任务状态
\rightarrow Skill 执行
\rightarrow 确定性验证
\rightarrow 沉淀证据与决策
\rightarrow 形成团队资产
\rightarrow 为下一次任务按需装配
$$

项目治理为执行提供可信上下文；执行流水线产生结构化轨迹；验证决定哪些轨迹值得升级为经验；团队记忆再把经过验证的经验送回未来任务。

这个闭环也改变了文档的经济性。过去团队文档经常因为短期价值不明显而失效。现在，一条准确的架构边界既能帮助新人，也能直接进入 Agent 的定位过程；一份测试规范既约束人工开发，也能成为自动验收规则。知识维护第一次可以在当前任务中立即产生回报，而不只是等待未来某位同事阅读。

## 五、不要把旧的软件工程常识重新包装成神话

删除死代码、简化架构、写清边界、完善测试、记录决策和控制权限，并不是 AI 时代才出现的方法。它们一直是良好软件工程的一部分。

AI 真正带来的变化有两个：

第一，它放大了模糊和混乱的代价。一个边界不清的需求，过去可能让开发者停下来询问；Agent 却可能在几分钟内生成一整套方向错误的实现。

第二，它降低了工程治理的边际成本。过去“不值得补”的测试、“没时间整理”的知识和“以后再清”的债务，现在可以由 AI 协助持续处理。很多长期正确、短期昂贵的实践因此重新具备经济可行性。

所以，AI 原生研发不等于追求更高的代码生成率。更可靠的衡量标准是：

- 项目中有多少隐含状态已经显式化；
- Agent 的关键判断有多少可以追溯到依据；
- 完成状态有多少由机器证据确认；
- 一次任务产生的经验有多少能在正确边界内复用；
- 错误资产能否被及时降权和撤回。

更实际的采用顺序是：先建立根目录索引和少量关键规则，再补验证闭环和状态落盘；当跨 Session、跨成员和重复试错成为真实成本后，才逐步引入资产分级、权限、版本和生命周期治理。

最终，AI 工程化的目标不是让模型知道一切，而是让它在当前任务中只拿到正确、足够、可验证的上下文。模型能力决定它能走多快，工程系统决定它是否走在正确方向上。
