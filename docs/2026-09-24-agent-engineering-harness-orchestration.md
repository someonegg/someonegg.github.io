# Agent 工程：从可靠执行到持续编排

当编程 Agent 能在短时间内完成大量实现，软件工程的瓶颈会逐渐从“谁来写代码”转向“怎样让工作持续朝正确方向推进”。这要求两个层次的设计：让单个 Agent 在仓库里可靠工作的 **harness**，以及让多个任务持续流转的 **orchestration**。

OpenAI 的 [Harness Engineering](https://openai.com/zh-Hans-CN/index/harness-engineering/) 记录了前者的实践；[Symphony](https://openai.com/zh-Hans-CN/index/open-source-codex-orchestration-symphony/) 则把 issue 跟踪器接到 Codex，探索后者。两篇文章合起来看，关键不是增加 Agent 数量，而是把人的判断转化为 Agent 能读取、执行和验证的环境。

## 一、先设计 Agent 能工作的环境

一次任务开始时，Agent 需要知道目标、现行架构、可用工具与完成标准。如果这些信息散落在聊天、个人记忆和过期文档中，再强的模型也只能猜测。

仓库应该提供一张可导航的地图：简短的 `AGENTS.md` 指向架构、产品约束、执行计划和操作指南；详细知识放在对应文档中，按任务需要读取。重要决策和失败经验要写回仓库，并定期检查文档是否仍与代码一致。文章中的团队发现，把所有规则塞进一份巨大的 `AGENTS.md`，反而会占用上下文、模糊优先级，并迅速失效。

环境还要让 Agent 看得见结果。能启动隔离的应用实例、驱动 UI、查询日志和指标、运行测试，Agent 才能复现问题并验证修复。否则，“完成”只是一次语言判断，而不是经过外部证据确认的状态。

## 二、把规范品味写成边界，而不是逐步指挥实现

> 通过强制执行不变量，而非对实施过程进行微观管理，我们令智能体能够快速交付，而且不会削弱基础。

> 人类的品味一旦被捕捉，就会持续应用于每一行代码。这也使我们能够每天发现并解决不良模式，而不是让它们在代码库中传播数天或数周。

人的工程判断无法完全交给规则，但其中可重复的部分应成为可执行的不变量。例如：模块只能按规定方向依赖；外部数据进入系统时必须校验；日志结构、文件大小和可靠性要求由 lint 或结构测试检查。规则说明“什么不能破坏”，让 Agent 在边界内自行选择实现。

这比为每次任务详细指定写法更有扩展性。一次设计评审中发现的反复出现的问题，可以沉淀为文档、测试或检查器；下一次任务便会自动收到同样的约束。检查器的报错也应说明如何修复，让反馈直接进入 Agent 的工作循环。

但规则不是越多越好。应优先固化影响正确性、可维护性和跨模块一致性的约束；局部表达方式留给具体任务。无法清楚解释价值的“品味”若被机械化，可能只会制造例外和维护成本。

## 三、让反馈比等待更快，同时守住风险边界

> 在一个智能体吞吐量远超人类注意力的系统中，纠错成本低，而等待成本高。

当 Agent 的产出速度超过人的审查速度，排队等待会吞掉新增的执行能力。文章中的团队因此缩短 PR 周期，让测试、Agent 审查和修复形成快速循环，并在合适的场景中用后续修正代替长时间阻塞。

这项取舍有前提：问题容易被发现，变更可回退，修复成本确实低于等待成本。安全、数据完整性、生产迁移等高后果变更，仍需要更严格的验证或人工判断。不能把“Agent 修得快”直接推导成“所有门禁都该放松”。

更好的完成标准是可检查的证据：测试结果、实际运行行为、截图或演示、日志与指标，以及未解决风险。Agent 可以执行和解释这些检查，但不能仅凭自述宣布通过。

## 四、把失败变成系统改进，并持续清理熵

> 我们没有手动修补这些结果，而是增加防护措施和技能，使智能体在下一次能够正确完成任务。

> 技术债务就像一笔高息贷款：不断地以小额贷款的方式偿还债务，总比让债务不断累积，再痛苦地一次解决要好得多。

Agent 会学习仓库中已有的模式，也会复制其中的坏模式。产出越快，架构漂移和重复实现就可能传播得越快。因此，技术债务治理应成为持续的小循环：发现偏差、定位共同原因、补上约束或工具、针对性重构，再验证新的规则是否有效。

对反复发生的失败，最有价值的修复通常发生在环境中。缺少测试，就增加能复现问题的测试；看不到运行状态，就改善可观测性；总是误用某个接口，就修正文档或 API 边界；同一类错误多次进入 PR，就将评审意见变成检查规则。这样，一次纠错会改变后续所有类似任务，而不只修好当前结果。

这类似持续的垃圾回收。小规模、频繁地偿还技术债务，可以减少坏模式成为下一个 Agent 的示例。人的“品味”只有被准确捕捉并持续维护，才会从一次性的评审意见变成长期有效的工程能力。

## 五、在可靠执行之上编排持续工作

> 一旦以这种方式对工作进行抽象，工单就可以代表更大粒度的工作单元。

> 将智能体当作状态机中的刚性节点并不是一个理想的模型，随着模型能力的提升，它们能够解决的问题远超我们试图限定的范围。

Symphony 处理的是下一层瓶颈：人难以同时记住并推动大量 Agent 会话。它以 issue 为工作单元，为符合条件的任务分配独立工作空间，并负责调度、重试和状态协调。具体开发流程写在仓库内的 `WORKFLOW.md` 中，由 Agent 使用工具执行；一个任务可以产生多个 PR，也可以只产出研究结果。

这种方式把人的注意力从“盯住每个会话”转向“定义目标、处理依赖、审查结果与例外”。任务树和依赖关系让未被阻塞的工作并行开展；长期运行的编排器负责接续中断的工作。但编排器无法替代前面的 harness：如果任务目标含糊、运行结果不可见、质量边界不可检查，持续调度只会放大这些缺陷。

Symphony 的开源内容是一份规范和参考实现，并非可以直接套用到任意仓库的完整产品。原文也指出，高度不确定或需要强专业判断的问题，仍适合由工程师直接参与交互式工作。

## 六、落地顺序

1. **先让仓库可理解。** 建立简短入口、现行架构说明和可追溯的任务计划，清理明显过期的信息。
2. **再让结果可验证。** 提供隔离运行环境、测试、UI 操作和日志指标，使 Agent 能拿出完成证据。
3. **固化高价值不变量。** 将重复出现的评审意见转为结构测试、lint 或明确的接口边界。
4. **建立持续清理循环。** 定期发现漂移，修复根因，并检验新规则是否减少同类问题。
5. **最后扩大编排。** 当单任务的质量反馈已经可靠，再用 issue 和工作流管理更多并行任务。

这条路径的核心衡量对象不是生成了多少代码或启动了多少 Agent，而是：在有限的人类注意力下，系统能否持续交付可验证、可维护的成果。环境、反馈回路和控制机制，决定了这种能力能扩展到什么程度。
